# Review round 4: PR #1534 — CollectLineageAction and action extras

Related issue: https://github.com/databrickslabs/dqx/issues/1266

Date: 2026-09-19

## Prior findings

- **Addressed:** Failed-column names stay in Spark through a temporary view; they are no longer collected into an unbounded Python list or inlined into SQL.
- **Partially addressed:** The column walk has a new guard for returns to a failed column, but it compares column names without their table names and can remove valid paths.
- **Still open:** The new `max_nodes` limits are inside the CTE members and at the tail, but they do not prove the claimed compute bound; the recursive member can still generate a large join result before its limit. The SQL form also needs validation on the stated DBR versions.

## Findings, sorted by severity

- **High — Column recursion drops valid paths when tables reuse a column name.** The new predicate `t.{frontier_col_key} NOT IN (SELECT col_name FROM <failed-columns view>)` (`src/databricks/labs/dqx/actions/lineage.py:785-793`) ignores the table. If `A.id` fails and lineage is `A.id → B.id → C.id`, the seed reaches `B.id`, then the recursive step rejects `C.id` because `id` is a failed column name. This is a common naming pattern and makes depth greater than one ineffective for those paths. Detect cycles using a fully qualified table-and-column identity in the path, including the anchor, rather than excluding a column name globally. Add a same-named-column multihop test.

- **High — New `LIMIT` placement may prevent the lineage CTEs from running.** Both generated statements put `LIMIT` directly before `UNION ALL` and again at the end of the recursive member (`src/databricks/labs/dqx/actions/lineage.py:619-638, 763-795`). The [Databricks recursive CTE syntax](https://docs.databricks.com/aws/en/sql/language-manual/sql-ref-syntax-qry-select-cte) specifies `base_case_query UNION ALL step_case_query`; the PR has no executed workspace test for this new member-level form. In SQL query grammar, a member-level `LIMIT` generally requires an explicitly parenthesized subquery, so this form is at substantial risk of parse or recursive-plan rejection. A failure would make every enabled table and column walk return `CONFIG_ERROR`. Verify the exact generated SQL on DBR 17 and supported later runtimes, and make the query shape valid there.

- **Medium — The compute-bound claim is still stronger than the implementation.** The member-level `LIMIT` caps rows returned by each member, but the recursive `JOIN system.access.*_lineage` must still find and process candidate edges before applying the limit (`src/databricks/labs/dqx/actions/lineage.py:628-637, 780-794`). For a high-fanout node, this can be expensive even with `max_nodes=100`. The code and guide claim the limits bound compute cost and intermediate expansion to `O(depth * max_nodes)` (`lineage.py:158-164, 598-601`; `docs/dqx/docs/guide/actions_and_alerts.mdx:532-538`). Narrow that claim to returned/materialized rows or establish a bound that applies before the expensive join.
