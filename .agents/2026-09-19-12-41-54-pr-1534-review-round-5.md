## Prior findings

- **Addressed:** The column cycle predicate now checks the anchor table as well as the failed column name (`src/databricks/labs/dqx/actions/lineage.py:805-811`), so same-named columns on other tables are no longer excluded by that predicate.
- **Addressed:** Failed-column seeds are kept in a session temporary view through the synchronous write, avoiding driver collection and an oversized literal `IN` list (`lineage.py:283-312, 390-403`).
- **Still open:** The recursive queries retain `LIMIT` inside both CTE members. Their validity and cost behavior on supported Databricks runtimes remain unverified.

## Findings, sorted by severity

- **High — Member-level `LIMIT` still needs a runnable Databricks validation.** Both generated recursive CTEs place `LIMIT` immediately before `UNION ALL` and at the end of the recursive member (`src/databricks/labs/dqx/actions/lineage.py:646-665, 780-813`). The documented [Databricks recursive CTE syntax](https://docs.databricks.com/aws/en/sql/language-manual/sql-ref-syntax-qry-select-cte) is `base_case_query UNION ALL step_case_query`; the PR's integration tests have not been run against the changed SQL. Without explicit grouping of member queries, this form risks parsing as a limit on the union or being rejected as an invalid recursive definition. Either use a query shape proven on DBR 17+ or execute the existing integration suite on a supported workspace before delivery. A query failure makes the action return `CONFIG_ERROR` and persist no lineage.

- **Medium — The column walk no longer has the promised total output cap.** The final column query ends at `SELECT DISTINCT ... FROM edges` without `LIMIT` (`src/databricks/labs/dqx/actions/lineage.py:813-816`), while the config and guide say `max_nodes` also caps total output (`lineage.py:158-164, 751-754`; `docs/dqx/docs/guide/actions_and_alerts.mdx:532-538`). If each member can contribute up to `max_nodes` rows over multiple recursion levels, column output can exceed `max_nodes`, and the subsequent `distinct_targets.collect()` and per-target history lookups scale with that excess (`lineage.py:537-546`). Restore a final cap or correct the contract and bound downstream work.

- **Medium — The claimed compute bound still excludes the expensive join.** A `LIMIT` on a recursive member's result does not prevent its join with `system.access.*_lineage` from reading and evaluating a high-fanout candidate set first (`src/databricks/labs/dqx/actions/lineage.py:656-665, 801-812`). The claimed `O(depth * max_nodes)` bound on compute/intermediate expansion (`lineage.py:158-164, 625-629`; guide lines 532-538) is therefore not established by this query. Describe the limit as a returned-row cap, or demonstrate a bound on the work before the join.
