## Findings, sorted by severity

- **High — Dense lineage graphs can cause unbounded traversal and output.** `LineageSearchConfig` no longer exposes `max_nodes`, and the recursive table-lineage query expands all paths up to `depth` without a node or row bound (`src/databricks/labs/dqx/actions/lineage.py:149-165, 595-615`). The column-lineage path also no longer caps its results (`lineage.py:712-717`). A small depth can still produce a very large number of paths in a dense graph, and the action then collects distinct targets on the driver and issues one `DESCRIBE HISTORY` per target (`lineage.py:494-513`). The action can therefore consume substantial compute or fail on realistic lineage graphs. Put a defensible bound on traversal and output, with a branching-graph test.

- **Medium — `depth=0` still emits table lineage.** The configuration says zero means no traversal (`src/databricks/labs/dqx/actions/lineage.py:153-156`), but enabled upstream/downstream searches always execute the anchor query at depth 1 (`lineage.py:595-603`). The recursive predicate only prevents subsequent hops. A caller requesting zero will still get direct neighbours.

- **Medium — The column search accepts a depth that has no effect.** `columns` uses `LineageSearchConfig`, whose `depth` is documented as maximum walk depth (`src/databricks/labs/dqx/actions/lineage.py:149-165, 191-193`). The column query only reads direct lineage and always emits `depth=1`, without consulting `search.depth` (`lineage.py:684-725`). Values of zero or greater than one behave identically. Either implement the documented column traversal or give columns a configuration that accurately describes direct-edge collection.

- **Low — Demo introduction still advertises removed modifier data.** The opening comment says the demo includes last-modifier job runs (`demos/dqx_demo_lineage_action.py:7`), although the action no longer collects them. Update the demo description before publication.
