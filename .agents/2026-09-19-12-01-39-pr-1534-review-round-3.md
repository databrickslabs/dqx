## Findings, sorted by severity

- **High — The `max_nodes` guardrail still cannot bound recursive query cost.** Both table and column walks put `LIMIT {max_nodes}` after the recursive CTE and `SELECT DISTINCT` (`src/databricks/labs/dqx/actions/lineage.py:614-635, 737-769`). Every path up to `depth` may be expanded before the limit applies. The new five-edge, depth-one test checks output row count only; it cannot detect explosive intermediate expansion. The code and guide now explicitly claim this post-CTE limit “bounds compute cost on dense graphs” (`lineage.py:157-160, 596-599`; `docs/dqx/docs/guide/actions_and_alerts.mdx:532-538`), which is incorrect. Apply a bound during expansion or make the depth/fanout limitation explicit without claiming a compute bound.

- **Medium — Column cycles can return to the failed anchor column.** The column CTE initializes `path` with only the first frontier node (`src/databricks/labs/dqx/actions/lineage.py:741-745`), then guards later frontier nodes against that path (`lineage.py:753-765`). For a downstream cycle `A.x → B.y → A.x` at `depth=2`, `A.x` is absent from the initial path, so the second edge is emitted as downstream lineage of the failed `A.x`. The table walk includes the anchor in its initial path. Seed the column path with both anchor and first frontier, and add a cycle regression test.

- **Medium — Failed-column seeds are collected without a size bound.** `_collect_column_lineage_df()` calls `failed_columns_df.collect()` and inlines every name in two SQL `IN (...)` clauses before applying `max_nodes` (`src/databricks/labs/dqx/actions/lineage.py:678-695`). For a large output table or many failing columns, this can create an oversized driver result and SQL statement. `max_nodes` does not constrain this step. Keep the seed set in Spark or apply an explicit bound with documented truncation semantics.
